# Communication and Learning

## Status Updates

Use a stable cadence and structure:

```markdown
Status:
Observed impact:
Affected scope:
Actions since last update:
Current mitigation and result:
Known uncertainty:
User or support guidance:
Next update:
```

Do not state a suspected cause as confirmed, promise an unsupported recovery time, or
expose sensitive implementation, participant, or security information.

## Timeline

Record declarations, role changes, observations, hypotheses, decisions, effects,
communications, recovery checks, and handoffs with one time standard. Preserve native
provider references and distinguish attempted, applied, failed, and unknown effects.

## Learning

After recovery:

1. Reconstruct the timeline from evidence rather than memory.
2. Describe impact and detection, response, and recovery performance.
3. Separate triggering event from contributing technical, process, organizational, and
   observability conditions.
4. Record what helped, what increased harm, where evidence was absent, and which
   defenses or assumptions failed.
5. Create bounded follow-up work with owners, verification, priority rationale, and
   links to the incident evidence.
6. Verify completed actions against the failure mode instead of closing them by status.

The review supports learning and risk reduction. It does not assign blame or guarantee
that the same symptom cannot recur through another path.
