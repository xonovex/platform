# formulation-run: Formulate Candidate Behavior and Requirements

## Core workflow

1. Resolve Discovery, Research, Decision, or other input references and revisions; apply [early-lifecycle-contracts.md](early-lifecycle-contracts.md).
2. Choose a neutral default method or load a selected method skill such as user stories, BDD, example mapping, jobs-to-be-done, or another compatible capability.
3. Express candidate behavior or requirements, examples, constraints, boundaries, qualities, and exclusions without changing their meaning to fit the chosen notation.
4. Mark ambiguities, conflicts, assumptions, and unresolved decisions explicitly. Request privacy, accessibility, security, architecture, or regulated-applicability intents when the profile requires them.
5. Review one coherent formulation slice with affected actors; preserve who supplied feedback and whether they had decision authority.
6. Publish a canonical Formulation result. Iterate by native revision until ambiguity is accepted, routed to Decision/Research/Design, or blocks progress.

## Boundaries

- Examples are evidence for clarity, not an automatic requirement to use Gherkin.
- A story-shaped artifact is one selectable representation; the canonical result remains Formulation.
- Models may draft and compare but cannot invent stakeholder agreement.
