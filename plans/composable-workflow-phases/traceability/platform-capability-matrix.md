# Platform Capability and Limitation Matrix

Last verified: **2026-07-14**

The matrix records documented native capabilities and known limits. It is not a substitute for adapter conformance tests against pinned platform versions.

| Platform | Source IDs | Native mechanism | Potential enforcement | Important limits | Required conformance |
| --- | --- | --- | --- | --- | --- |
| Claude Code | S-HARNESS-CLAUDE | Command, prompt, agent, HTTP and MCP-tool hook handlers; broad lifecycle event surface | Command/HTTP handlers can deterministically allow/deny at supported events; actual guarantees are event-specific | Agent hooks are experimental; matching hooks may run concurrently; sibling side effects cannot be assumed to short-circuit | Pin tested version; verify event payloads, exit/result semantics, concurrency, managed settings and bypass paths |
| Codex | S-HARNESS-CODEX, S-CODEX-PLUGINS, S-CODEX-MANAGED | Lifecycle command hooks and plugin/managed hook packaging | Command hooks provide deterministic interception at documented events | Current docs state prompt and agent handlers are parsed but skipped; matching command hooks may run concurrently; project hooks require trust | Test only command handlers as enforceable until official behavior changes; verify trust and managed precedence |
| Kiro | S-HARNESS-KIRO | Shell-command and agent-prompt actions across file, prompt, tool, task, session and stop events | Blocking depends on event/action behavior | Agent-prompt actions introduce model nondeterminism; platform behavior/version must be tested | Probe events, blocking, context mutation, failure, timeout and permissions |
| GitHub Copilot CLI/cloud agent | S-HARNESS-COPILOT | Repository and personal shell-command hooks | Supported before-action hooks may approve/deny according to documented contract | Shell-command model; supported events differ by surface/version | Test CLI and cloud-agent surfaces separately; verify event payload and repository trust |
| OpenCode | S-HARNESS-OPENCODE | JavaScript/TypeScript plugins with session, permission, shell and tool-before/after events | Plugin code can intercept/modify supported operations | Executable plugin trust, permission and event-order behavior require explicit review | Test plugin permissions, event ordering, failures, bypasses and version compatibility |
| Pi | S-HARNESS-PI | TypeScript extensions, skills, prompt templates and packages | Depends on installed extension/package behavior | No mandatory built-in sandbox, permissions or subagent model; governance must be supplied explicitly | Require module trust, isolation declaration and package-specific tests |
| GitHub Actions/repository controls | S-GITHUB-REUSABLE, S-GITHUB-RULESETS, S-GITHUB-ENV, S-GITHUB-SECURE | Reusable workflows, composite actions, required checks, rulesets and protected environments | Repository/org and deployment controls can enforce shared requirements | Feature/account availability and permissions vary; reusable workflow ref pinning matters | Pin by commit SHA where appropriate; test least privilege, protected branches/environments and artifact evidence |
| GitLab CI/CD/compliance | S-GITLAB-COMPONENTS, S-GITLAB-PIPELINE-POLICY, S-GITLAB-COMPLIANCE | Versioned components, typed inputs, pipeline execution policies and compliance frameworks | Policies can inject/enforce jobs and compliance behavior | Availability, precedence and merge semantics vary by GitLab version/tier | Pin tested version; validate component inputs, policy precedence, bypass paths and evidence |
| Azure DevOps Services/Server | S-AZDO-TEMPLATES, S-AZDO-APPROVALS, S-AZDO-BRANCH, S-AZDO-WORKITEMS, S-AZDO-SERVICE-CONNECTIONS, S-AZDO-REST, S-AZDO-SERVICE-HOOKS | Boards work items, Repos/pull requests, Pipelines/templates/checks, artifacts, service connections, REST and service hooks | Branch policies, build validation, approvals/checks, protected resources and organization/project permissions | Services and Server versions differ; account plan, process customization, API version and identity mode vary | Detect Services/Server and version; test work-item links, PR policies, templates, approvals, service connection identity, APIs, hooks and evidence references |
| Bitbucket Cloud | S-BITBUCKET-CLOUD-PIPELINES, S-BITBUCKET-CLOUD-OIDC, S-BITBUCKET-CLOUD-DEPLOY, S-BITBUCKET-CLOUD-MERGE, S-BITBUCKET-CLOUD-BRANCH, S-BITBUCKET-CLOUD-SHARED, S-BITBUCKET-CLOUD-CUSTOM-CHECKS, S-BITBUCKET-CLOUD-REST, S-BITBUCKET-CLOUD-WEBHOOKS | Repositories/PRs, Pipelines, shared configurations, OIDC, deployments, merge checks, branch permissions, REST and webhooks | Merge checks, branch permissions, deployment restrictions and pipeline status | Workspace plan, runner, custom-check and shared-config capabilities vary; webhook ordering/retries and API limits apply | Test plan/tier, pipeline config, OIDC claims, merge/deployment gates, build statuses, REST scopes, webhook signatures/retries and native references |
| Bitbucket Data Center | S-BITBUCKET-DC, S-BITBUCKET-DC-REST | Self-managed projects, repositories, PRs, permissions, build status, REST and installed-app integrations | Native branch/merge permissions and server-side policy; exact capability depends on version/apps | Must not inherit Bitbucket Cloud Pipelines/OIDC/custom-check assumptions; deployment version and plugins vary | Detect version and installed apps; test REST, authentication, PR/build status, permissions, webhooks/plugins and upgrade compatibility |
| Bitrise | S-BITRISE-WORKFLOWS, S-BITRISE-SECRETS, S-BITRISE-ARTIFACTS, S-BITRISE-TRIGGERS, S-BITRISE-OIDC-AWS, S-BITRISE-BUILD-STATUS, S-BITRISE-VERIFIED-STEPS | Mobile CI Workflows/Pipelines/Steps, triggers, secrets, artifacts, statuses, API/webhooks, OIDC and hosted/self-hosted runners | Trigger/config controls, secret exposure controls, build status and release/approval features where enabled | Workspace plan, stack/runner, PR-secret policy, self-hosted boundary and Step provenance vary | Test project/workspace capabilities, trigger precedence, secret exposure, OIDC claims, artifact access/retention, build status and Step/version trust |
| AWS | S-AWS-IAM-BEST, S-AWS-OIDC, S-AWS-SCP, S-AWS-CLOUDTRAIL, S-AWS-CONFIG, S-AWS-SECURITY-HUB | IAM roles/federation, Organizations guardrails, CloudTrail, Config and Security Hub | IAM/resource policy, permissions boundaries/SCPs, organization controls, audit/config/security checks | SCPs limit but do not grant permissions; account/region/organization configuration and service coverage vary | Test OIDC trust claims, role permissions, temporary credentials, organization guardrails, audit trail, Config/Security Hub evidence, rollback and break-glass |
| Datadog | S-DATADOG-CI, S-DATADOG-CD, S-DATADOG-OTEL, S-DATADOG-AUDIT, S-DATADOG-CATALOG, S-DATADOG-AWS, S-DATADOG-CLOUD-SECURITY, S-DATADOG-LLM, S-DATADOG-DORA | CI/CD visibility, OTel, LLM observability, audit, software catalog, AWS integration, cloud security and DORA metrics | Mostly evidence/observability; monitors, roles and product-specific controls can support policy but are not a universal enforcement boundary | Product tier, ingestion volume/cost, retention, regions, sensitive content, supported integrations and source-of-truth ownership vary | Test API/app keys and roles, collection/redaction, service correlation, CI/deployment/LLM event mapping, AWS integration, retention/access and failure behavior |
